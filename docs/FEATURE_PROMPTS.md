## 3. Ручная оценка (без сдачи файла/теста)

Нужна сущность "ручная оценка": курс, тема, студент, балл, опциональный комментарий (переиспользуй поле комментария из предыдущей фичи), кто и когда поставил. По клику — модалка: балл + опциональный комментарий, сохранение через новый эндпоинт. Отображай ручные оценки в тех же местах, где обычные оценки за сдачу (журнал/список сдач), с пометкой, что оценка выставлена вручную (без файла).

## 10. Лента курса: объявления + неизменяемый журнал материалов

Цель: учебный процесс прозрачен. Если преподаватель загрузил лабораторную, студенты сделали работу, а потом файл заменили или удалили — это должно остаться в истории. Студент и администратор должны доказать, что материал менялся.

Вкладка на фронте уже называется «Лента курса». Она читает `GET course-feed/{courseId}/`. Пока эндпоинта нет, фронт собирает ленту из объявлений и текущего списка файлов (удаления/замены в этом режиме не видны).

### Backend промпт
Расширь объявления курса до ленты событий курса. Сохрани текущие CRUD объявлений (`course-announcements/{courseId}/`) без ломания контракта.

1. Добавь неизменяемый журнал учебных материалов (не ответы студентов). Модель события: id, course, author (кто сделал действие), kind (`material_created` | `material_updated` | `material_replaced` | `material_deleted`), дата создания, snapshot файла: `file_name`, опционально `previous_file_name` при замене, `theme` {id, title}, опционально ссылка на файл, если он ещё существует. **Записи журнала нельзя редактировать и удалять** ни преподавателю, ни API удаления материала — удаление файла только добавляет событие `material_deleted`, старая запись о загрузке остаётся.

2. Пиши события автоматически:
   - преподаватель загрузил файл в тему → `material_created`;
   - заменил тот же материал другим файлом → `material_replaced` (старое имя в `previous_file_name`, новое в `file_name`);
   - изменил метаданные файла без замены содержимого → `material_updated`;
   - удалил учебный материал → `material_deleted` с именем и темой на момент удаления.
   Не логируй сдачи студентов.

3. Эндпоинт `GET course-feed/{courseId}/` для всех участников курса. Ответ — плоский массив (или `{ items: [...] }`) смешанных записей, отсортированных по `created_at` desc. Закреплённые объявления (`is_pinned: true`) всегда сверху, затем хронология. Query-параметры: `sort=desc|asc` (по `created_at`), `kind=announcement|materials|all` (фильтр). Каждая запись:
   ```
   {
     "id": "uuid",
     "kind": "announcement" | "material_created" | "material_updated" | "material_replaced" | "material_deleted",
     "created_at": "ISO-8601",
     "updated_at": "ISO-8601 | null",
     "author": { "id", "full_name", "avatar", ... } | null,
     "is_pinned": false,
     "can_manage": false,
     "text": "только для announcement",
     "material": {
       "id": "id файла или null если уже удалён",
       "file_name": "lab.pdf",
       "previous_file_name": "old_lab.pdf | null",
       "file": "url или null",
       "theme": { "id": "...", "title": "Лабораторная 1" }
     }
   }
   ```
   Для объявлений `can_manage` как сейчас; для событий материалов всегда `can_manage: false`.

4. Права: читать ленту — участники курса. Писать объявления — преподаватель/сопреподаватель. Журнал материалов пишет только сервер при add/update/delete материала.

5. Уведомления: при создании объявления — как сейчас, type «Объявление курса», ссылка `/courses/{courseId}/feed/` (или `/announcements/` — фронт оба понимает). При add/replace/delete материала — уведомление участникам с type одним из: «Добавлен материал курса», «Изменён материал курса», «Удалён материал курса», тот же link на ленту. Текст: кто, какой файл, какая тема.

6. Миграция: старые объявления остаются в ленте как `kind=announcement`. Для уже существующих файлов один раз создай `material_created` по `uploaded_at` (или дате создания), без дублей при повторном деплое.

7. События журнала не удаляются каскадом вместе с файлом или темой: тема в snapshot остаётся текстом даже после удаления темы.

### Frontend промпт
Вкладка «Лента курса» читает `GET course-feed/{courseId}/` с `sort` и `kind`. Объявления по-прежнему через `course-announcements`. Клиентский fallback из файлов не используется.

## 8. Случайная выборка из банка вопросов (только frontend)

### Frontend промпт
Backend не трогать — итоговый тест по-прежнему создаётся с явным фиксированным списком ID вопросов, как сейчас. В диалоге выбора вопросов из банка добавь режим «Случайная выборка»: преподаватель выбирает банк/категорию и количество вопросов N, нажимает "Сгенерировать" — из отфильтрованного списка доступных вопросов на клиенте случайно выбираются N штук и подставляются в текущий выбор (как будто препод отметил их вручную). Дай возможность перегенерировать выборку до сохранения. Дальше форма сохранения теста работает как раньше, отправляя обычный список ID вопросов — никакой новой логики на сервере не появляется.

## 7. Новые типы вопросов (верно/неверно, короткий ответ, развёрнутый ответ)

### Backend промпт
Расширь модель вопроса банка/теста типом вопроса (enum), добавив к существующим single/multiple choice три новых типа: "верно/неверно" (одна булева правильная опция), "короткий ответ" (эталонный текст ответа, проверка на точное совпадение при сравнении, без учёта регистра и лишних пробелов), "развёрнутый ответ" (свободный текст, без автопроверки — требует ручной проверки преподавателем). Обнови сериализаторы вопросов и логику проверки ответов при прохождении теста: для верно/неверно и короткого ответа — автоматическая проверка как раньше, для развёрнутого — ответ сохраняется как есть и не засчитывается баллом автоматически, отметь его как "требует проверки", чтобы преподаватель мог поставить балл и комментарий вручную (используй уже существующий механизм ручной оценки/комментария). Сохрани полную обратную совместимость со старыми вопросами single/multiple choice — их поведение не меняется.

### Frontend промпт
В редакторе вопросов (банк вопросов и редактор теста) добавь выбор типа вопроса с тремя новыми вариантами и специфичной формой для каждого: верно/неверно — переключатель правильного ответа; короткий ответ — поле ввода эталонного текста; развёрнутый ответ — только текст вопроса, без указания правильного ответа. В интерфейсе прохождения теста студентом отрисовывай подходящий инпут под каждый тип (переключатель, текстовое поле, многострочное поле). В интерфейсе проверки ответов преподавателем добавь отображение ответов на развёрнутые вопросы как требующих ручной проверки, с возможностью поставить балл и комментарий через существующий механизм ручной оценки.

Никаких графиков — только табличное представление, как в бумажном журнале.
